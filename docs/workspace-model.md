# Workspace model

## 경계

워크스페이스는 폴더나 최상위 문서가 아니라 Nyxdoc의 테넌트 경계다. 다음 항목은 반드시
하나의 워크스페이스에 속하며 다른 워크스페이스와 암묵적으로 섞이지 않는다.

- 문서 트리와 내부 문서 링크
- 사람 멤버와 역할
- 전역 에이전트가 이곳에서 갖는 멤버십, 역할, 세부 권한과 문서 범위
- 문서 담당, 저장 필터, presence
- 미디어, 휴지통, 감사 기록과 관리 요청

문서는 폴더 역할도 하지만 워크스페이스는 문서 트리보다 한 단계 위다. 따라서
`gameroom` 워크스페이스 안에 `gameroom`이라는 루트 문서가 있을 수 있으며, 둘은 이름이
같아도 서로 다른 개념이다.

## 설정 소유권

| 설정 | 소유자 | 위치 |
| --- | --- | --- |
| 공개 URL, 가입 도메인, 이메일 인증, SMTP 비밀 경계 | Nyxdoc 사이트 | 사이트 관리 |
| 표시 이름, 개인 아바타, 로그인 보안 | 사람 계정 | 계정 설정 |
| 개인 에이전트 신원·아바타·연결 키·키 상한·IP 제한 | 개인 네임스페이스 | 에이전트 메뉴 |
| 조직 정보·멤버·초대·팀·감사 기록 | 조직 | 조직 설정 |
| 조직 에이전트 신원·키와 개인 에이전트 BYOA 승인 | 조직 | 조직 설정 |
| 워크스페이스 이름과 정책 | 워크스페이스 | 워크스페이스 설정 |
| 에이전트 배정·역할·세부 권한·허용 문서 트리 | 워크스페이스 | 워크스페이스 설정 |
| 관리 요청과 감사 기록 | 워크스페이스 | 워크스페이스 설정 |
| 워크스페이스 생성 | 사람 계정 | 전역 워크스페이스 선택기 |
| 현재 워크스페이스 삭제 | 워크스페이스 소유자 | 워크스페이스 설정 |
| 삭제된 워크스페이스 복구·영구 삭제 | 사람 계정 | 통합 휴지통 |

에이전트 신원과 연결 키는 계정에 속하며 워크스페이스와 독립적이다. 한 에이전트를 여러
워크스페이스에 배정할 수 있고, 같은 키로 접근할 수 있다. 연결 URL의
`x-nyxdoc-workspace-id` 헤더 또는 `workspace` 쿼리는 기본 워크스페이스만 정한다. 문서 ID,
Task ID, 저장 보기 ID, 담당 ID가 있는 도구는 실제 리소스에서 워크스페이스를 자동 판별하고,
목록·검색·생성처럼 대상이 모호한 도구는 호출 인자의 `workspaceId`를 우선한다. 둘 다 없을
때만 연결 기본값을 사용한다. 대상 워크스페이스에 활성 배정이 없으면 접근할 수 없다.

사람이 브라우저에서 열어둔 워크스페이스는 개인 UI 상태이며 에이전트의 기본값, 허용 범위,
도구 라우팅에 아무 영향도 주지 않는다. 따라서 한 연결로 여러 허용 워크스페이스를 오가며
작업할 때 사용자가 브라우저 화면을 전환할 필요가 없다.

실제 허용 행동은 `키 scope 상한 ∩ 키의 선택적 워크스페이스/IP 제한 ∩ 워크스페이스별
역할·세부 권한 ∩ 선택적 문서 하위 트리`의 교집합이다. “워크스페이스 전체”는 계정 전체가
아니라 선택된 워크스페이스의 현재 및 미래 문서 전체를 뜻한다.

전역 에이전트나 키를 변경하면 그 에이전트가 배정된 각 워크스페이스의 감사 기록에도
전역 변경임을 표시해 남긴다. 키 원문과 해시는 감사 메타데이터에 기록하지 않는다.

일반 사용자는 이 분리를 여러 화면을 오가며 직접 조립하지 않는다. 워크스페이스의
`에이전트 연결` 흐름이 `신원 선택/등록 → 역할·문서 범위 → 기존 키 재사용/새 키 생성 →
워크스페이스가 명시된 MCP 주소`를 안내한다. 서버는 이 과정을 하나의 트랜잭션으로 적용한다.
에이전트 메뉴는 이름·아바타·키 회전·IP 제한 같은 계정 전역 고급 관리에 사용한다.

워크스페이스 소유자는 개인 또는 조직이다. 조직 멤버십은 문서 접근 권한이 아니며,
조직 워크스페이스는 사람 또는 팀을 `viewer`, `editor`, `admin`으로 명시적으로 배정한다.
여러 grant가 겹치면 가장 높은 역할이 적용된다. 조직 소유 에이전트와 승인된 개인 BYOA도
해당 조직의 워크스페이스에만 배정할 수 있다. 자세한 계약은
[organization model](organization-model.md)을 참고한다.

워크스페이스 생성은 현재 워크스페이스의 하위 작업처럼 보이지 않아야 한다. 따라서 현재
워크스페이스 설정 안에 생성 버튼을 두지 않고, 모든 화면의 전역 워크스페이스 선택기에
`＋ 새 워크스페이스`를 둔다. 생성 뒤 에이전트 연결은 선택 단계이며, 연결을 완료하거나
건너뛰면 새 워크스페이스를 선택한 문서 화면으로 끝난다.

접근 권한, 담당 지정, 현재 작업 상태도 분리한다.

- 역할과 연결 키 범위: 무엇을 할 수 있는가
- 담당 지정: 어떤 문서의 책임자인가
- presence: 지금 무엇을 하고 있는가

## 선택과 안정적인 링크

사용자가 마지막으로 선택한 워크스페이스는 브라우저에 기억한다. 워크스페이스 전환은
문서 목록, 에이전트, 키와 운영 기록을 함께 바꾼다. 문서 ID가 포함된 링크는 문서의 실제
워크스페이스를 우선하므로 감사된 워크스페이스 이전 후에도 기존 북마크가 유지된다.

문서 목록 패널의 너비, 스크롤 위치와 펼친 문서 상태는 워크스페이스·화면별 사용자 UI
상태다. 문서를 전환하거나 Yjs 공유 초안 세션을 안전하게 다시 마운트해도 이 상태를 유지하며,
문서 정본이나 워크스페이스 데이터에는 기록하지 않는다.

## 삭제와 복구

통합 휴지통은 특정 워크스페이스의 설정 화면이 아니라 계정이 접근할 수 있는 모든 활성
워크스페이스의 삭제 문서를 워크스페이스별로 묶고, 소유자가 삭제한 워크스페이스도 같은
화면에 표시한다. 문서 복구·영구 삭제 권한은 각 워크스페이스 역할에서 계산하며,
워크스페이스 생명주기는 소유자만 조작한다. 활성 워크스페이스를 삭제하는 진입점은 해당
워크스페이스의 설정에만 두고, 통합 휴지통에는 실제 `trashed` 상태가 된 워크스페이스만
표시한다.

워크스페이스 삭제는 hard delete가 아니라 `active → trashed` 상태 전이다. 소유자만 실행할 수
있고 마지막 활성 워크스페이스는 삭제할 수 없다. 삭제 즉시 사람·에이전트·MCP·공유 초안
접근을 모두 차단하지만 문서 ID, 트리, 리비전, 초안, 미디어, 사람·에이전트 멤버십, 저장
필터와 감사 기록은 그대로 보존한다. 복구는 같은 ID와 관계를 유지한 채 `trashed → active`로
되돌린다.

영구 삭제는 휴지통 상태의 워크스페이스만 대상으로 하며 소유자가 정확한 워크스페이스 이름을
다시 입력해야 한다. 서버는 DB와 미디어의 전체 백업 세대를 먼저 만들고 무결성을 검증한
뒤에만 워크스페이스 경계를 한 트랜잭션으로 제거한다. 독립적인 purge tombstone에는 당시
이름, 문서·멤버·에이전트 배정·미디어 수, 삭제자와 검증된 백업 세대 ID를 남긴다. 연결 키와
전역 에이전트 신원은 계정 자산이므로 삭제하지 않고, 해당 워크스페이스 배정과 키 allowlist
참조만 제거한다.

## 워크스페이스 이전

일반 UI에서 워크스페이스 사이 문서 이동은 제공하지 않는다. 운영 이전은 문서 하나가 아니라
완결된 경계를 옮기는 명시적 작업이다. `workspace:transfer`는 기본적으로 dry-run이며 다음을
하나의 작업으로 검증한다.

- 루트와 모든 하위 문서, 블록, 리비전, 이벤트, 내부 링크
- 해당 에이전트의 워크스페이스 멤버십과 이전 대상에 묶인 호환 메타데이터
- requestId 재시도 기록, 담당 지정, 사용 중인 미디어
- 범위 밖 링크·리비전·이벤트·키 범위·업로드가 없는지
- 대상의 slug/미디어 충돌과 모든 테넌트 불변 조건

적용할 때는 정확한 예상 행 수와 루트 ID 재확인을 요구한다. 운영 DB를 쓰기 전에 검증된 백업
세대를 만들고 그 복제본에서 동일 작업을 먼저 통과시킨다. 실제 적용은 한 트랜잭션이며 양쪽
워크스페이스 감사 로그와 백업 세대의 receipt를 남긴다. 문서 ID, 리비전 번호·스냅샷,
작성·수정 시각과 기존 전역 에이전트 ID, 연결 키 원문/해시는 바꾸지 않는다.

이전할 에이전트가 정본 트리 밖의 과거 QA 문서에도 기록을 남겼다면 그 출처를 조용히 지우거나
정본 워크스페이스로 끌고 가지 않는다. 범위 밖 문서가 모두 이미 보관 상태인 경우에만 별도의
비활성 보관 에이전트와 폐기된 보관 키로 리비전·이벤트·requestId·미디어 업로드 출처를 먼저
분리한다. 이후 기존 에이전트와 실제 키에는 정본 기록만 남겨 그대로 대상 워크스페이스로
옮긴다. 이 분리 역시 예상 행 수 확인, 백업 복제본 사전 실행, 단일 트랜잭션과 감사 기록의
적용을 받는다.
