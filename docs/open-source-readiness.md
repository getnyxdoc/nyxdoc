# Open-source newcomer readiness

Checked against Nyxdoc `0.25.20` (`package.json`) and the current scripts and
workflows. This is the detailed path for a first-time user or contributor;
the README keeps the short path and links here.

## The first five minutes

### 0:00 — choose a supported path

For a self-hosted trial, use Linux with Docker Engine and Docker Compose v2.
The checkout and lifecycle path uses Bash and Git; the installer checks Docker
Compose v2, `awk`, `sed`, and `curl`, while the updater also needs Git and
`sha256sum`. The deployment guide calls for at least 1 GB of available memory
and a persistent host backup directory. Windows and macOS Docker Desktop, and
native Node execution, are development-only/best-effort environments. They are
not supported targets for the lifecycle scripts, backup recovery, or production
operation; use a Linux host or VM for those paths.

For local development, use Node.js 24 and npm instead of Docker Compose.

### 0:30 — install

```bash
git clone https://github.com/getnyxdoc/nyxdoc.git && cd nyxdoc && ./scripts/install.sh
```

The installer copies `.env.production.example` when needed, creates two
different secrets without printing them, selects the versioned GHCR image tag
matching the checked-out `package.json` version, starts `app`, `collaboration`, and
`gateway`, and waits for the public gateway plus the internal collaboration
health check. To build the checkout
instead of pulling the release image:

```bash
./scripts/install.sh --build
```

Open <http://localhost:3191>. The first account becomes the site owner; SMTP
and a custom email domain are not required. After that, registration is
invite-only by default.

### 2:00 — connect the first agent

After signing in, open **Settings → Workspace → Agent access → Connect the
first agent**. The wizard has three source-verified stages:

1. Choose an existing agent identity or register a new one.
2. Choose the workspace access profile (`Reader`, `Drafter`, or `Writer`) and
   the document scope. The default scope is every document in the workspace.
3. Attach an existing compatible key, create a new connection key, or attach
   a key later.

When a new key is created, Nyxdoc shows the raw value only once. Copy the
generated private handoff or store the value in the agent's secret store. The
handoff contains the workspace-default MCP URL, Streamable HTTP transport,
Bearer authentication, and verification instructions. The manual Codex form
generated by the UI is:

```toml
[mcp_servers.nyxdoc]
url = "https://your-nyxdoc.example/mcp?workspace=<workspace-id>"
bearer_token_env_var = "NYXDOC_TOKEN"
```

Use the handoff or client-specific configuration rather than putting the raw
key in a repository, document, shell history, log, or chat transcript.

### 4:00 — verify the connection

Ask the connected client to call `get_capabilities` first, then
`list_agent_workspaces`. The first response is the runtime contract; the
second confirms the effective workspace grants and document scopes. Use
`workspaceId` for ambiguous list/search/create operations when more than one
allowed workspace exists. A human's currently open browser workspace does not
route agent calls.

For a first safe demonstration, use `Reader` to read an existing document. If
you chose `Writer`, have the agent create a draft, review it, and explicitly
commit the canonical revision; `Drafter` is limited to shared drafts. Do not
ask an agent to start a queued Agent To-do unless a person explicitly requested
that work.

## Lifecycle commands and sharp edges

These commands are implemented by the lifecycle scripts and are safe to
copy from the repository checkout:

```bash
./scripts/update.sh
./scripts/uninstall.sh
./scripts/uninstall.sh --purge --confirm-purge=nyxdoc
```

For an installation still on `0.25.17` or `0.25.18`, run the current release
bridge from the checkout so accepted collaboration writes are drained before
the old updater's backup:

```bash
curl -fsSL https://raw.githubusercontent.com/getnyxdoc/nyxdoc/v0.25.19/scripts/update-bootstrap.sh | bash
```

Use `./scripts/update.sh` for every later release.

`update.sh` requires a clean Git checkout. It normally requires a running app
so it can create and verify a pre-update backup; after an interrupted update it
can resume only when the persisted receipt matches the same source/target and
the backup verifies again. The default channel follows the newest canonical
remote `vX.Y.Z` release tag. The script only moves forward to a descendant
revision. For the source-only main channel, it requires the explicit form:

```bash
./scripts/update.sh --channel main --build
```

Normal uninstall removes containers and the Compose network while preserving
the data volume, backups, environment, and source. Purge removes the Docker
data volume and locally built images; it requires the exact confirmation flag.
If the app is running, purge creates and verifies one final external backup.
The external backup directory, `.env.production`, and source checkout remain;
delete those separately only after a verified recovery copy exists.

### Backup and restore are explicit

Create a generation and verify it from the running Linux Compose installation:

```bash
docker compose --env-file .env.production exec -T --user node app npm run backup:create
docker compose --env-file .env.production exec -T --user node app \
  npm run backup:verify -- /backups/<generation-id>
```

Restore is deliberately not a shortcut that overwrites a live installation.
Use empty, isolated database and media paths and repeat the generation ID as an
explicit confirmation:

```bash
docker compose --env-file .env.production exec -T --user node app npm run backup:restore -- \
  /backups/<generation-id> \
  --database /tmp/nyxdoc-restore/nyxdoc.db \
  --media /tmp/nyxdoc-restore/media \
  --confirm-generation <generation-id>
```

The command verifies the generation before restoring and will not overwrite
different existing targets; an existing target is accepted only when it already
matches the confirmed backup. Restore into a fresh volume or isolated paths,
then start and verify that copy before any planned recovery of a live service.

## Local development and contributor checks

```bash
npm ci
cp .env.example .env.local
npm run dev
```

The app is at <http://localhost:3100> and the collaboration service is at
`127.0.0.1:3101`. The repository declares these quality commands:

```bash
npm run typecheck
npm run lint
npm test
npm run test:lifecycle-cli
npm run build
```

For editor changes, install the Chromium browser used by CI before running the
browser suite:

```bash
npx playwright install chromium
npm run test:editor-e2e
```

On Linux CI, use `npx playwright install --with-deps chromium` so the required
system libraries are installed as well.

The pull-request template also asks for the four general checks and the editor
suite when relevant. Database changes must use forward-only migrations.

## Community and release orientation

- Bug reports require a version or commit, installation type, reproduction,
  expected behavior, and actual behavior. Use synthetic data and redact keys,
  passwords, private documents, databases, and production logs.
- Feature requests ask for the problem, proposed outcome, human/agent
  workflow, and alternatives. Blank issues remain enabled for cases that do
  not fit a template.
- Security reports go to the private address in `SECURITY.md` and the issue
  form; they should not be opened publicly.
- Release qualification is documented in
  [`testing-and-release-qualification.md`](testing-and-release-qualification.md).
  CI runs static checks, integration checks, Compose lifecycle checks, and
  release qualification against an immutable candidate image before promotion.
  The immutable digest is the CI promotion boundary; normal `install.sh` and
  `update.sh` use the matching versioned release image tag.

## Review findings and follow-up recommendations

The following are concrete documentation or release-hygiene follow-ups, not
claims about missing product capabilities:

1. Keep the version in all README variants, `.env.production.example`, and
   deployment examples synchronized whenever a release is cut.
2. Consider requiring a version-like value in the bug template instead of the
   stale `0.24.1` placeholder, and link the release-qualification document from
   the contributor landing path.
3. Add a redacted screenshot of the first-agent connection wizard. The current
   README screenshots accurately show document editing and Agent To-do, but not
   the connection path that is most likely to block a newcomer.

## Verification boundary

The documented npm script names were compared with `package.json`, lifecycle
shell scripts passed `bash -n`, and the disposable CLI lifecycle contract ran
migration, backup, verification, restore, and idempotent retry against an
isolated database and media tree. The UI-generated handoff/configuration was
compared with the settings components and MCP route. Docker Compose could not
be executed in the review environment because the Docker CLI was unavailable;
the Compose claims above were checked against `compose.yaml`,
`compose-common.sh`, `DEPLOYMENT.md`, and the Linux Compose CI job instead.
